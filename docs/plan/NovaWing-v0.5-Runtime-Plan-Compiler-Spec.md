# NovaWing v0.5 — Frozen Plan to existing Runtime

## Contract

Phase 3 reads one `verifyPlanSnapshot`-verified `PlanSnapshot`. Compilation never reads a mutable `DevelopmentPlan` and never creates a WorkSession. The frozen plan stays frozen. Delivery artifacts have their own lifecycle and live under the NovaWing data root's `delivery` directory.

`PlanSnapshot → DeliveryTargetBinding → CompiledRuntimePlan → RuntimeAdmission → explicit Start Delivery → existing WorkSession Runtime`.

The target binding records the canonical Git root and Git directory identity, exact HEAD, branch or detached state, clean/dirty state, platform, selection source and binding time. Paths and Git state are outside the frozen semantic hash. The binding ID is stable for the same snapshot and target Git state. `new_project` is represented but is not admitted in this phase. An existing repository must be clean and on the bound branch and commit before Start Delivery.

## Lossless mapping

Every PlannedTask becomes one RuntimeTaskBinding with title, complexity, requirement IDs, objective, outputs, dependencies, criterion IDs and assertion IDs. Every source AcceptanceAssertion retains a coverage binding for each relevant task, including its exact observable behavior, expected outcome, expected evidence and effective blocking value. Exactly one covering task owns the assertion: the unique task that transitively depends on every other covering task. Other tasks contribute but cannot create another obligation or PASS verdict. Parallel covering tasks without a unique owner produce `OWNERSHIP_AMBIGUOUS` and block Start. Full RequirementClause, AcceptanceCriterion and customer decision copies remain in the compiled plan. Admission recomputes the complete binding set against the verified snapshot and rejects missing, extra or changed task, requirement, criterion, assertion, decision or baseline facts. The WorkSession definition gives the Executor and Reviewer the frozen plan hash, relevant RequirementClause and AcceptanceCriterion content, customer decisions and exact blocking assertion IDs and outcomes. Tasks are sent to the existing Runtime in dependency order.

An assertion is `SUPPORTED` only when a trusted resolver supplies an assertion-scoped verifier command accepted by the command policy. `SUPPORTED` still produces an immutable obligation before Start; its exact blueprint and executable evidence are bound at the owner implementation commit. A command is an evidence collection method; the assertion still names the customer behavior and outcome. The default resolver classifies UI and platform assertions as `REQUIRES_EXTERNAL_ENVIRONMENT` and other assertions as `UNSUPPORTED`, so Customer Mode cannot invent acceptance coverage. A trusted resolver can also declare `REQUIRES_HUMAN`. Blocking gaps produce `ADMISSION_BLOCKED`, not a compilation error. The existing scoped Node verifier is not restored.

Phase 6.1 admission model version 2 uses `PROVISIONABLE_DURING_EXECUTION`. Before Start, each local blocking assertion has one immutable, hashed `VerificationObligation`. It freezes assertion and criterion identity, canonical owner and covering tasks, provider ID and version, strategy, predicate class, exact frozen outcome and evidence text, mutation/reread/entity/number/cleanup/fresh-state flags, external residual, allowed binding inputs, forbidden substitutions, target Git identity and baseline ancestry, and the deadline before owner Task completion. The strategy comes from a closed vocabulary: assertion-scoped repository test, loopback GET predicate, scoped artifact predicate, owned process predicate, or delivery scope review. Missing strategy, predicate class, expected text, flags, exact numbers, provider, owner, or forbidden substitutions is `UNRESOLVED` and blocks Start. An implementation-dependent test file or endpoint need not exist at Start. A GET cannot stand in for a mutating scenario; negative scope cannot be proved by one missing file.

The delivery Runtime makes a guarded implementation commit C before VERIFY, using only files from its trusted repository inspection. The existing Task-boundary checkpoint verifies this commit rather than trying to commit a second time. The exact `VerificationBlueprint` is provisioned against clean C, with the bound baseline as an ancestor. The repository inspector supplies artifact SHA-256 hashes and a generated scope manifest. A repository contract candidate must pass the unchanged strict deterministic rules plus obligation conformance, an independent blueprint review of bounded source, and at most two repairs. The approved blueprint and the `PROVISIONABLE_DURING_EXECUTION → BOUND_EXECUTABLE` transition are persisted once by obligation ID, with C, blueprint hash and artifact hashes. Provisioning cannot change the obligation or RuntimePlan identity. A later descendant commit preserves a completed task only while its bound artifacts remain unchanged; artifact drift invalidates its evidence until reverified.

All delivery tasks are HIGH risk in the existing V2 Runtime. The Task Completion gate requires every owned local assertion to have an approved blueprint, durable transition, NovaWing-executed matching evidence at C, and independent per-assertion `PASS` whose `capabilityEvidence.evidenceIds` link to that evidence. Missing, duplicate, unexpected or failed verdicts block completion. Completion-only external or human assertions receive `DEFERRED` only; they may reach `LOCALLY_VERIFIED` so downstream development can continue, while the customer acceptance ledger keeps them open. An execution prerequisite still blocks Start. The Runtime checks this gate immediately before finalizing a Task and durably records local completion. Existing verification, repair, re-review and checkpoint mechanisms remain authoritative.

The Customer Delivery Completion gate is separate. All Tasks must be locally verified; each unique external or human assertion and each local assertion with an external residual also needs accepted external or identified human evidence and independent review. `DEFERRED` never becomes `PASS` automatically. Missing or invalidated evidence yields `CUSTOMER_DELIVERY_BLOCKED`. The delivery status API includes the customer assessment.

## Identity and persistence

`runtimePlanHash` is SHA-256 over canonical semantic content: source snapshot and plan hash, target Git identity and baseline, compiler schema and implementation version (`0.5.0-phase6.1`), admission model version 2, runtime policy version, task and acceptance mappings, the obligation set hash, requirements and customer decisions. Blueprint hashes belong to their durable transitions and never enter the RuntimePlan hash. Audit timestamps and randomly generated event IDs are excluded. Binding, compiled plan, admission result and WorkSession source binding are persisted as private local JSON artifacts. On read, hashes and source coverage are checked again; readiness rechecks the current target and capabilities without silently recompiling.

Start Delivery requires exact snapshot ID and plan hash, RuntimePlan ID/hash and target binding ID. It rechecks admission and claims a deterministic WorkSession ID with an exclusive persisted marker before calling the existing Launchpad WorkSession creation path. A duplicate completed request returns the same session. An interrupted `STARTING` claim refuses another creation until explicit reconciliation, avoiding duplicate execution. The trusted WorkSession configuration is persisted separately for the existing Runtime's restart path. The target baseline is checked before configuration creation and again just before the WorkSession controller starts.

## Customer and telemetry boundary

The frozen Customer page offers a project folder path, readiness check, plain-language blockers and an explicit Start Delivery button only when ready. The current local web surface has no safe cross-platform folder picker, so the path input is the bounded fallback; Desktop can later supply a picker through the same binding API. No model, Reviewer or shell options are shown to the customer. The server accepts the same local authenticated mutation token as planning writes.

Delivery telemetry emits only event name, snapshot ID, short RuntimePlan hash and bounded counts/duration. It never records target paths, raw requirements, customer answer text, prompts, responses, source code or secrets.

## Limits

The real Requirement 001 repository is not an execution fixture. This phase only recompiles and admits it read-only; no WorkSession or customer repository mutation is performed. No general business verifier is inferred from `npm test`, a route name, or an exit code. The web folder input and `new_project` target type need future product work. External or human evidence remains deferred until a trusted provider or identified human decision is available.
